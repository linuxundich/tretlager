# QA audit Tretlager – 2026-10-30

Audited state: 0.8.0 (Flatpak) plus `[Unreleased]`, commit `37323ff`. Tested on tinytin
(TUXEDO OS Forky, Plasma 6.7.4 Wayland, Intel + RTX 3050 Ti, BT stick TP-Link UB500, Wahoo
KICKR V4, Wahoo TICKR, Garmin HRM-Pro Plus) and by code review.

Labels: **reproduced** = recreated and measured on tinytin; **code** = unambiguous from the source
code, not specifically recreated; **risk** = plausible, not proven.

## 1. Overall assessment

Tretlager keeps its core promise: one click starts Zwift under Wine with NVIDIA graphics, and the
bridge passes the trainer and heart rate strap to Zwift via Wahoo Direct Connect, without the
Companion app. Architecture, error handling around the token and the UI are surprisingly clean for
the age of the project (two days). The biggest weakness was in the bridge: a single absent sensor
blocked Bluetooth for all others for up to 40 s per attempt (fixed). What remains open are mostly
things only real tests can settle: other distributions and GNOME, standby, long rides.

## 2. Technical state

- Core (`tretlager/core`) without UI, UI (`tretlager/kde`) as a thin PySide layer, bridge
  (`tretlager/bridge`) as a separate process via D-Bus activation. Long-running work runs in
  threads, results come back via Qt signal (queued) – the UI does not block.
- 128 tests, all green in the Flatpak on tinytin (locally without bleak 117 + 2 skipped).
- Weaknesses: `kde/app.py` (≈700 lines) bundles six areas in one class `Backend`; the sensor state
  is polled via a `gdbus` process instead of subscribing to the existing D-Bus signal `Changed`;
  `setup.Context.run` only checks its timeout when the process prints something.

## 3. Qt/KDE integration

Kirigami + Kirigami Addons (FormCard, AboutPage, ContextualHelpButton, PromptDialog,
GlobalDrawer) throughout, no custom widgets except the page scaffold `ColumnsPage` and the sensor
row `DeviceDelegate`, both justified (width, fixed row height). i18n via a Python replacement for
`KLocalizedContext`. Dark/light come from the Plasma color scheme (no hard-coded colors, state
colors from `Kirigami.Theme`). HiDPI: Wine DPI from the XWayland scaling.

## 4. BLE bridge and devices

- Standard services FTMS, Cycling Power, CSC, Heart Rate are passed through raw to Zwift;
  control point responses (ERG, grade) correctly in the DIRCON write response.
- An adapter lock serializes scanning and connecting (BlueZ does not cope with parallel
  operations).
- Tested: KICKR V4 (FTMS incl. ERG/grade), TICKR, HRM-Pro Plus (reliable only via the USB stick,
  the known AX201 incompatibility is shown). Technically supported but untested: other FTMS
  trainers, standalone power meters (CPS), CSC sensors, combined devices. ANT+ not supported.

## 5. Zwift integration

Start via SilentLaunch + RunFromProcess (game as a child of the launcher), token only via a 0600
file, update detection via `Zwift_ver_cur.xml` with a reflink snapshot, graphics path from the
graphics test, KWin script for maximizing. Zwift files are not modified (only the Wine registry:
DPI, XRandR/XVidMode off, EGL off with NVIDIA).

## 6. Flatpak and distribution independence

The manifest builds Wine 11.20 from source (WoW64), Python packages as pinned wheels with
checksums, no `--filesystem=home`, no `--device=all`. Bluetooth only via
`--system-talk-name=org.bluez` (no raw access), Avahi via the system bus, Zwift runs in the same
sandbox. Tested only on TUXEDO OS Forky; Fedora, Ubuntu, openSUSE, Arch and GNOME are unverified.
Host requirements are now in the README.

## 7. UI/UX and design

Clear sidebar (Overview, Sensors, Help | Check setup, About); without scrolling, the overview shows
start, sensors with live values and Zwift state. Linear assistant with step indicator. Weaknesses:
the start area claimed “Ready to ride” even when sensors were missing (fixed); the main action is
a normal-sized button and does not stand out visually.

## 8. Usability and workflow

Everyday use: open Tretlager → bridge starts in advance → *Start Zwift* (sign-in, update, start,
maximizing all automatic) – one click. The direct launcher “Zwift (Tretlager)” saves even that.
Known sensors reconnect automatically. Good help right where it is needed (“Troubleshooting”).
Several devices of the same kind are allowed; the bridge announces each one separately.

## 9. Performance and stability

Measured on tinytin:

| State | before | after |
|---|---|---|
| UI idle (window open) | ≈ 2.5 % of one core (1.3 % itself + 1.2 % gdbus children) | unchanged (live values visible) |
| UI during the ride | 1.5 s polling + `wine tasklist` every 5 s | 0.4 % (17 + 9 ticks in 60 s) |
| Bridge with 2 connected sensors | 0.4 % | – |
| `Scan(3)` with one absent, enabled sensor | 40–63 s | 11 s |
| Heart rate dropout due to the absent sensor's lock | 59 s (13:26:04 → 13:27:03) | none in 4 runs |

RSS: UI ≈ 300 MB (QtWebEngine loaded), bridge ≈ 30 MB.

**Test ride with the fixed Flatpak (13:55–13:59, by me, tinytin on Wi-Fi only):**
Zwift paired the KICKR (power, cadence) and the TICKR via the bridge; 38 commands to the FTMS
control point (30 × grade `0x11`, plus control/start/reset), all acknowledged by the trainer, none
without a response. No bridge warning during the ride. Zwift exited at 13:59:00, detected by
Tretlager at 13:59:11, bridge stopped at 13:59:16, window stayed open (normal start). Not achieved:
10 minutes duration, strap dropout during the ride.
Observation: before the ride the TICKR needed three connection attempts (two timeouts of 40 s
each, found but no connection established), then stable – probably the strap without skin
contact; not caused by B-01 (the lock only holds this device), but keep an eye on it.

## 10. Privacy and security

No telemetry. Network connections: `cdn.zwift.com` (version, installer), `secure.zwift.com`
(sign-in), GitHub (winetricks, pinned by commit + SHA-256), winetricks download sources (once),
reachability check against `cdn.zwift.com` and GitHub. Installer verified via Authenticode against
“Zwift, Inc.”. Token in the Secret Service, never in files or logs; a residual risk is the token on
the command line of `ZwiftApp.exe`. By default the bridge only listens on 127.0.0.1; “Offer on the
network” opens trainer control to the LAN without authentication (explained in the UI).

## 11. Findings by priority

### P1

**B-01 Absent sensor blocks Bluetooth for up to 40 s per attempt** – bridge – *reproduced, fixed*
- Steps: TICKR and KICKR connected, resume the HRM-Pro (not worn), `Scan(3)` via D-Bus.
- Expected: scan finished after ~3 s; other sensors reconnect immediately.
- Actual: `Scan(3)` 40.0 / 43.0 / 63.4 s; the TICKR lost its connection and was only back after
  59 s.
- Cause: `BleakClient(adresse).connect()` first searches for the device with the connection timeout
  (40 s) while holding the adapter lock `connect_lock`.
- Fix: own address lookup with `FIND_TIMEOUT = 8 s`, then connect with 40 s
  (`bridge/device.py`). Afterwards: `Scan(3)` 11 s, no dropout.

### P2

**Z-01 End of the ride: monitoring could die, Zwift was looked up via a Wine program** – start – *code, fixed*
- `wine tasklist` every 5 s during the ride; a timeout (30 s) ended the monitoring thread
  silently → UI would hang at “Zwift is running”, no cleanup.
- Fix: `launch.process_running()` reads `argv[0]` from `/proc` (only up to the first null byte,
  the token comes after it), two failures in a row = exited, exceptions caught.
- Found and confirmed during implementation: `comm` is useless, Zwift is called `main` there, the
  launcher `ZwiftLauncher.e`. Real run afterwards: Zwift kept running, exit detected in ≈ 10 s
  after quitting, bridge stopped, direct launcher closed.

**Z-02 Unexpected exception during start did not clean up** – start – *code, fixed*: this path now also calls `after_exit()`.

**L-01 Without internet it said “Session expired, please sign in”** – sign-in – *code, fixed*
- Access token expired (after 6 h), renewal fails due to the missing network → `valid_token()`
  returned `None` → prompt to sign in again.
- Fix: `LoginUnavailable`; offline the message is “Zwift sign-in unreachable. Is there an internet
  connection?”. Test `test_valid_token_offline_raises_instead_of_login`.

**L-02 Without a running keyring the sign-in page hung** – sign-in – *code, fixed*
- `secretstorage` exceptions were not `LoginError`s; the thread died, “busy” stayed set.
- Fix: understandable message (KWallet or GNOME Keyring must be running and unlocked).

**B-02 A broken `bridge.json` takes down the bridge** – bridge – *code, fixed*
- JSON errors or unknown fields (older/newer version) → exception at start → no bridge.
- Fix: move the file aside as `bridge.defekt`, start empty; ignore unknown fields.

**B-03 Technical error texts in the UI** – bridge/sensors – *code, fixed*
- Raw BlueZ/gdbus texts (`org.bluez.Error.NotReady`, `GDBus.Error:…`) appeared in the sensor row
  and on the sensors page.
- Fix: `device.describe_error()` and `bridgectl.describe_dbus_error()`; raw text goes to the bridge
  journal or `tretlager.log`.

**U-01 Sensor polling every 1.5 s even during the ride** – UI – *measured, fixed*
- Two `gdbus` processes per poll. Fix: 15 s while Zwift is running or the window is minimized
  (under Wayland Qt does not always report minimizing, so the ride counts as well).
- Better in the long run: subscribe to the bridge's `Changed` signal via QtDBus (available in the
  Flatpak).

**U-02 “Ready to ride” regardless of the sensor state** – overview – *reproduced (screenshot), fixed*
- Fix: “Ready to ride” only if all enabled sensors are connected, otherwise “Almost ready” with
  “2 of 3 sensors connected. Still searching: …”.

**B-04 On every BLE dropout the device disappears for Zwift** – bridge – *risk, fixed later*: 45 s grace period; verified live (KICKR disconnected via BlueZ, DIRCON client stayed connected, data back after 17 s)
- `_teardown()` withdraws the mDNS announcement and the DIRCON server on every disconnect; Zwift
  has to reconnect. Proposal: keep the server and announcement for 30–60 s, only pause the data.
  Needs a test ride with a deliberate dropout.

**B-05 Standby/resume and unplugging the stick during the ride untested** – bridge – *risk, open*

**F-01 `--talk-name=org.kde.KWin` is far-reaching** – Flatpak – *risk, open*
- Allows KWin scripts, i.e. interference with all windows. Used only for maximizing. Check
  alternatives: set the Wine window size ourselves or do without maximizing.

**F-02 GNOME and other distributions untested** – Flatpak – *open (F2b/F5)*: no maximizing outside Plasma, DPI only from the window scaling.

**S-02 Token on the command line of ZwiftApp.exe** – security – *known (BACKLOG), open*

### P3

**S-01 Single-instance socket accepted commands from any local user** – *code, fixed*: abstract sockets have no permissions; now checked via `SO_PEERCRED`.

**I-01 Untranslated texts** (setup: “… installieren”, “winetricks laden”, GB progress, “schon erledigt”, unexpected errors, secretstorage) – *fixed*.

**I-02 Legacy message “Reinstall the tretlager package”** on the sensors page – *fixed* (never reachable). Further Debian leftovers: `check_wine` outside the Flatpak, `PreparePage` – open.

**C-01 `Context.run` timeout only checked on output** – *code, fixed later* (watchdog thread): a silent, hanging process (e.g. winetricks) would not be aborted.

**C-02 DIRCON writes without backpressure** – *risk, fixed later* (discarded above 64 kB of buffer): if Zwift hangs, the send buffer grows.

**U-03 Main action visually small** – *proposal, open* (see 14).

**Z-03 Snapshot before updates without a space check** – *code, resolved by removal*: on ext4 every snapshot would have been a full copy (7.4 GB). By my decision there are no snapshots anymore; instead the setup is reconciled before every start, and rollback goes via Flatpak (`docs/updates.md`).

**T-01 QML messages “i18n is not defined” on exit** – only observed in the screenshot tool (context object torn down before the engine), harmless.

## 14. Recommended next steps

1. Long ride (≥ 30 min) with deliberate strap and stick dropouts; then B-04 (grace period).
2. Bridge state via QtDBus signal instead of polling; split `Backend` into sub-objects (sensors,
   start, sign-in, setup).
3. F5: Fedora KDE/GNOME and Ubuntu in VMs (run without NVIDIA/Bluetooth), Arch on smokki.
4. Design, within the KDE HIG (no custom tiles):
   - Larger start button (`Kirigami.Units.gridUnit * 2` high, `display: TextBesideIcon`), as the
     only highlighted button on the page.
   - Larger live sensor values in the overview with tabular figures (watts, rpm, heart rate as a
     key figure, unit small underneath) – that is the “sporty” information.
   - Sensor row status dot additionally as text for color-blind users (already shown next to it)
     and as Accessible.name.
5. Clarify F-01 (KWin permission) and investigate S-02 (token handover) in the Zwift launcher.
